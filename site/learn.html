LVL in one sitting

If you can read a little code and a little law, you can finish this in twenty minutes and write your own programs afterward. An LVL program is a small world: declare who exists, state what happened (with a source and a confidence), write the rules of law, and ask questions.

Hello, dispute

Here is a complete, runnable program. Every keyword in it is explained below.

hello.lvl
jurisdiction IN.Contract.v1

party A = Person "Anil Kumar"
party B = Person "Beena Rao"

fact transfer_17 : TransferOfValue {
    from: A  to: B  amount: INR 1_000_000  on: 2025-03-10
} from source(doc="BankStatement_3", page=2, para=4) status Established

claim c_loan by A : "the transfer was a loan" asserts Loan(transfer_17)

evidence w17 : Message { author: B  text: "I'll repay you next month." }
    from source(doc="WhatsApp_17", para=21) supports RepaymentObligation(transfer_17)

rule loan_definition:
    Loan(t) requires TransferOfValue(t) RepaymentObligation(t)
rule repayment_obligation:
    RepaymentObligation(t) established_if AdmittedRepayment(t) or ContractRequiresRepayment(t)

assert Loan(transfer_17) under BalanceOfProbabilities

The building blocks

jurisdiction names the rule library in force. party declares the people and organisations — the nouns of your world.

parties.lvl
party A = Person "Anil Kumar"
party acme = Org "Acme Labs Pvt Ltd"

fact states something that happened. Two LVL-specific questions come attached: where is it in the record? (from source(...)) and how firmly is it accepted? (status). Declaring a fact also asserts the proposition of its type — TransferOfValue(transfer_17).

fact.lvl
fact transfer_17 : TransferOfValue {
    from: A  to: B  amount: INR 1_000_000  on: 2025-03-10
} from source(doc="BankStatement_3", page=2, para=4) status Established

claim is a party's contention (weak on its own). evidence is a document, message, or testimony that supports or refutes a proposition.

claim-evidence.lvl
claim c_loan by A : "the transfer was a loan" asserts Loan(transfer_17)

evidence w17 : Message { author: B  text: "I'll repay next month." }
    from source(doc="WhatsApp_17", para=21) supports RepaymentObligation(transfer_17)

rule is the law itself. Two shapes cover most legal logic: requires (all elements — a conjunction) and established_if (any branch — a disjunction). A lowercase, undeclared argument like t is a variable.

rules.lvl
rule loan_definition:
    Loan(t) requires
        TransferOfValue(t)
        RepaymentObligation(t)

rule repayment_obligation:
    RepaymentObligation(t) established_if
        AdmittedRepayment(t)
        or ContractRequiresRepayment(t)

Contracts are mostly duties, so LVL has deontic nodes: obligation, permission, prohibition.

deontic.lvl
obligation notify {
    bearer: Receiving  to: Disclosing
    that: NotifyOnRequest(Receiving)  by: 2025-07-01
}
prohibition keep_secret {
    bearer: Receiving  that: Discloses(Receiving)
    on_breach: liable(Receiving, damages)
}

Asking questions

Questions are the primary way humans use an LVL program. Write them in the file, or run them from the command line over any existing program. Answers are never a bare yes/no — they're a status plus a derivation trace, every leaf tied to the record.

lvl assert hello.lvl
⚖  assert  Loan(transfer_17)   standard: BalanceOfProbabilities

  Loan(transfer_17) ............................. SUPPORTED
    └─ requires: TransferOfValue(transfer_17) ∧ RepaymentObligation(transfer_17)
      TransferOfValue(transfer_17) .............. ESTABLISHED
        └─ Established fact (transfer_17)  →  BankStatement_3 p.2 ¶4
      RepaymentObligation(transfer_17) .......... SUPPORTED
        └─ supporting evidence (w17)  →  WhatsApp_17 ¶21

  RESULT: SUPPORTED  ✓ (meets BalanceOfProbabilities)
assert / prove

Does it hold, to a standard of proof?

refute

Is it disproven?

explain

The full derivation tree for any proposition.

discover

Which elements of a claim are still missing?

The epistemic lattice

An LVL proposition is never just true. It carries a status, ordered from worst to best support, and is judged against a standard of proof.

StatusMeaning
Refutedevidence shows it's false
Unsupportedasserted, nothing backs it
Unknownno information (the default)
Disputedevidence points both ways
Supportedevidence in favour, not conclusive
Proven / Establishedestablished to the required standard

requires takes the weakest element (an argument is only as strong as its weakest part); established_if takes the strongest branch. A civil claim clears at Supported (BalanceOfProbabilities); a criminal charge needs Proven (BeyondReasonableDoubt). A Disputed proposition never meets any standard until the conflict is resolved.

Objective checks & conflicts

Some things need no legal judgement — they're arithmetic and calendars. constraint compares money, numbers, and dates directly.

constraints.lvl
constraint damages_within_cap: disclosure.amount <= nda.penalty_cap
constraint disclosure_in_term: disclosure.on before nda.expires_on

Conflicts surface two ways: evidence that supports and refutes the same proposition makes it Disputed; and an exclusive { } set that both hold triggers a violation. Run lvl check-contradictions.

exclusive.lvl
exclusive { Loan(transfer_17) Investment(transfer_17) }

Compare two documents

Turn two versions of a contract into programs, then ask whether they mean the same thing. equiv compares both the conclusions and the operative terms, ignoring cosmetics; diff gives the full delta.

lvl equiv v1.lvl v2.lvl
⚖  equiv  service-agreement-v1  ≟  service-agreement-v2

  ✗ DIFFERENT — they diverge on these propositions:
    · term changed — agreement.fee: INR500000 → INR650000
    · rule added — penalty_clause

Convert your document into LVL

Don't try to write the whole program at once. Make five cheap passes over the document, each producing one kind of node. An LLM can do this — see the LLM kit — but the method is the same by hand.

  1. Parties. Every person and organisation → a party.
  2. Facts. Every event/state the document treats as having happened → a fact, with source(...) and a status matching the document's own hedging.
  3. Claims & evidence. Separate contentions (claim) from proof (evidence ... supports/refutes). Mark incompatible characterisations exclusive.
  4. Rules. Encode the legal tests as rules. Do not fabricate elements — leave unsupported ones unstated so they evaluate to Unknown.
  5. Constraints & questions. Objective relations → constraint; the ultimate issues → assert ... under the right standard.
The golden rules. Cite everything (no source → not a fact). Never inflate confidence beyond the document. Encode the logic you can, and leave genuine open questions Unknown for a human. Then lvl check, fix, and read the trace — never present a bare conclusion.

Syntax reference

KeywordPurpose
jurisdictionwhich rule library is in force
partydeclare a person/org
factstate something that happened (+ source + status)
evidencesomething that supports / refutes a proposition
claima party's contention
rule … requiresconjunction (AND) of elements
rule … established_ifdisjunction (OR) of branches
obligation / permission / prohibitiondeontic duties
constraintobjective money/date/number comparison
exclusivepropositions that cannot co-exist
assert / prove / refuteask whether something holds
explain / discovertrace it / find what's missing

Whitespace is insignificant; comments are # or //. Full grammar: spec/grammar.ebnf.
