Theory & design

Is JVL a "real" programming language?

Short answer: yes, but a deliberately restricted one — and the restriction is the whole point. This page answers the questions that matter when you design a language to check the law: is it Turing complete, does it always terminate, is it decidable, and what actually makes a language good for this job.

Is JVL Turing complete?

No — and that is a feature, not a limitation. A language is "Turing complete" if it can express any computation a Turing machine can: unbounded loops, arbitrary recursion, general memory. C, Python, and JavaScript are Turing complete. The price of that power is a famous theorem: for a Turing-complete language you cannot, in general, decide whether a program will halt, or whether two programs compute the same thing. These questions are undecidable.

JVL is intentionally not Turing complete. It has no unbounded loops, no general recursion over infinite data, no mutable memory. A JVL program is a finite set of facts and rules over a finite set of declared entities. Evaluating it is a bounded process that always finishes.

Why would you give up power? Because the questions you undertake by giving it up — "does this always halt?", "do these two contracts mean the same thing?", "is this set of clauses consistent?" — are exactly the questions a legal checker must answer, and they are only decidable in a non-Turing-complete language. JVL trades power it doesn't need for guarantees it can't live without.

The best languages for verification are the restrained ones

JVL is in excellent company. Some of the most useful languages ever built are deliberately less powerful than a general-purpose language, precisely so they can be analysed:

You would never want the program that decides whether you owe money, or whether an offence is made out, to be one that might loop forever or whose meaning cannot be compared to another. A contract is not a Turing machine, and it should not be encoded as one. What you want is a decision procedure: give it the facts, and it always returns an answer, with a reason.

Where JVL sits on the power spectrum

Formally, JVL's rule layer is close to Datalog with stratified/defeasible negation, extended with an epistemic-status lattice and objective constraints over finite values. That places it here:

Propositional logic→ JVL · Datalog · SQL→ Prolog (Turing complete)→ Python / C (Turing complete)

Moving right adds expressive power and takes away decidability. JVL sits at the sweet spot: expressive enough to capture the logical skeleton of law (conjunction, disjunction, defeasible defaults, provenance, objective comparison), restrained enough that every question about a program is answerable.

It always terminates

JVL evaluation is a forward-chaining fixpoint. It repeatedly applies the rules until nothing changes. Because the set of entities is finite and the epistemic lattice has finite height, there are only finitely many states the program can be in, and each pass either changes something or halts. So evaluation is guaranteed to reach a fixpoint and stop — no program can hang. (The reference evaluator also carries a hard iteration cap as a belt-and-braces safeguard.)

Everything about a program is decidable

Because JVL isn't Turing complete, the questions that are undecidable for real programming languages are decidable for JVL:

  • Does a proposition hold? — evaluate to fixpoint, read the status. Always answerable.
  • Are these clauses consistent? — check for any Disputed atom or violated exclusive set. Always answerable.
  • Do two contracts mean the same thing? — compare the derived state of both. Always answerable (jvl equiv).

That last one is worth dwelling on. Program equivalence is undecidable for Turing-complete languages — it's a corollary of the halting problem. JVL can answer it because it gave up the power that made it undecidable. The feature you liked — "check if two legal documents say the same thing" — exists because JVL is not Turing complete.

It is deterministic

The fixpoint does not depend on the order rules are written, and there is no randomness or hidden state. The same program yields the same answer and the same derivation trace, every run, on every machine. For a system meant to make the law's mechanical part actually mechanical, this is non-negotiable — and it's what makes jvl emit json a reliable interchange format and diff/equiv trustworthy.

So what actually makes JVL a good language?

Not raw power. For this job, the properties that matter are:

Decidability

Every question about a program has an answer the compiler can compute.

Termination

Evaluation always halts. A legal checker that might hang is useless.

Determinism

Same input, same answer, same explanation — always.

Soundness

It only derives what actually follows; unsupported things stay Unknown.

Readability

Two audiences — a lawyer and a language model — must both parse it unambiguously.

Auditability

Every conclusion traces to a source. Power without provenance is dangerous.

Expressiveness still matters — the language has to be able to say what the law says. But it's a tension to be balanced, not maximised: expressive enough to capture legal logic, restrained enough to stay checkable. Every proposed feature is judged against that line. If a construct would make equivalence undecidable or evaluation non-terminating, that's a strong reason against it.

Scale and complexity

Since a JVL program is just data plus rules, it can be arbitrarily large — a whole contract suite, a constitution, a treatise. Evaluation is a fixpoint over a finite universe, so its cost is polynomial in the size of the program (for bounded predicate arity, like Datalog). In plain terms: it scales. A bigger document is more facts and rules, not a fundamentally harder problem, and an assertion still runs over all of it.

The reference evaluator binds rule variables by matching against the atoms that actually exist, so evaluation scales with the relevant facts rather than the size of the document — a program with 5,000 facts evaluates in about 90 ms (reference-impl/bench.py). Further gains (incremental re-evaluation for simulate, indexed multi-variable joins) are engineering on a well-understood foundation, and on the roadmap. The in-browser engine runs whole programs instantly.

When would we add more power?

Some legal structures want bounded recursion — transitive relationships like corporate ownership chains ("A controls B, B controls C, therefore A controls C"). That's expressible in Datalog and stays decidable, so it's a natural extension. What JVL will keep resisting is unbounded computation — general loops and arbitrary recursion — because that's exactly what would forfeit termination and equivalence-checking. The guiding rule: add expressiveness only while every question about a program stays answerable.

The one-line version. JVL isn't Turing complete because it doesn't want to be. It wants to always halt, always give a reason, and let you ask whether two documents mean the same thing — and those are precisely the powers a Turing-complete language has to give up.
